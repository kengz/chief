# Fleet

## 1. Native Codex dispatch

1. **Discover capabilities before dispatch.** Use the application's native project listing to resolve the project, host, root and repository status. Where available, `list_projects`, `create_thread`, `read_thread`, `wait_threads` and `send_message_to_thread` provide these operations. Names and availability depend on the installed application; missing capabilities go to the owner, never a hand-built agent launcher.
2. **Chief owns dispatch; execution hosts run project sessions.** Chief extensions use the active coordinator as relay until direct host control and application visibility are verified. Give one authorized session its purpose, checkout, current instructions, checks, memory/task budget, time/cost cap, instructing owner and terminating result. Chief creates a separate native session and isolated work for each independent lane from the lead’s ownership plan, parallelizing within aggregate admitted capacity; the lead coordinates integration. Approved SSH may inspect or configure infrastructure; it does not dispatch agents through `codex exec`.
3. **Read acceptance by identity.** Keep the returned host/thread identity; a pending client identity cannot address a ready session. A session launched at a projects root must enter its assigned checkout or worktree and explicitly read the applicable global, parent and project `AGENTS.md` files plus the current work list before work; changing directory alone does not prove loading. Reload changed guidance before further work. Read acknowledgment of owner, scope, exact checkout and instruction files read, and verify application visibility. Delivery or process success is insufficient.
4. **Follow-ups require human authorization.** Native send delivers; native read and wait observe. Agent messages do not authorize messages back to another session. Timers may observe and hold text, never dispatch. Read the current work list before each step.
5. **Verify effective approval and sandbox policies.** Preserve authentication, filesystem and network restrictions. If the owner explicitly authorizes unattended `never` approval policy, inspect existing configuration and profile overrides before changing only that field. Authorized managed setup may constrain `allowed_approval_policies = ["never"]` in `/etc/codex/requirements.toml`; preserve existing requirements, privately back up preimages and atomically publish complete bytes. Official `configRequirements/read`, where supported, checks decoding; actual creation and follow-up turn contexts must prove effective policy and sandbox. Repeat after a controlled server restart. Configuration text alone is insufficient; changing approval policy does not authorize broader access.

## 2. Runtime and source setup

6. **Inspect CLI and application server separately.** Save and inspect the official installer at `https://chatgpt.com/codex/install.sh`, verify the selected release and integrity, then use its documented noninteractive interface: `CODEX_NON_INTERACTIVE=1 sh installer.sh --release <verified-version>`. Verify actual login-shell PATH, `codex --version` and supported daemon version reporting. Installation must not launch agent work; retain old releases and existing processes until a reviewed transition.
7. **Use supported lifecycle control in an accepted idle window.** Check loaded sessions, background terminals and descendants before an update or restart. Confirm command help for the installed version. No broad process matching, force signals, socket deletion or invented daemon state. A legacy exception requires exact identity, official source proof, independent review and explicit ownership of affected work; otherwise stop and report the missing control. After shutdown, allow only a bounded native bootstrap under fresh capacity checks, then verify replacement identity, containment, preserved history and effective policy before follow-up. OS reboot qualification is separate.
8. **Toolkit installation is separate from runtime.** Fetch the reviewed pin; verify clean tracked state, ancestry and untracked collisions before fast-forward. Preserve divergence and unknown files: no stash, destructive reset, clean or force push. A synced-equal exception requires reviewed full source/index preimages, target-equal dirty files, enumerated old-clean updates, immediate race guards and whole-tree target equality before metadata-only adoption. Prove unrelated bytes and modes remain unchanged. Install once and check in the actual login environment: exit 0 with no `NOTE` or `NOT CHECKED`. Investigate failures instead of rerunning unchanged commands to green.

## 3. Admission and containment

9. **Choose limits from the actual host.** Measure total/available memory, current charges, reclaimable cache, swap, tasks, pressure, other work and control topology. Reserve OS/control headroom; no fixed host capacities ship with this template. Verify all worker and reconnect paths fall inside the selected execution boundary. Dedicated service limits are insufficient if native autostart escapes them. An outer user boundary includes shells and other user work; saturation can deny their forks or logins even with root SSH outside. Preserve existing work while staging limits and use bounded positive/negative tests, never host stress or an OOM test.
10. **Before each creation or follow-up, run a reviewed read-only host admission check.** Declare memory and task budgets, compare actual aggregate headroom plus recovery reserve, pressure, live/persistent limits and daemon/worker ancestry. Run it from the dispatcher through approved host inspection outside the worker sandbox: namespace-mapped ownership is not host proof. Unknown identity, escaped work, insufficient room or changed policy fails closed. Serialize decisions and account for overlapping sessions. A manual snapshot neither reserves capacity nor intercepts native dispatch; it cannot guarantee unbounded work fits. A host-specific mechanical checker needs its own reviewed policy and meaningful refusal tests; this template supplies no deployment checker or installed limits.

## 4. Retained adapter transport

11. **Discover the adapter's own verbs and scope.** For an explicitly approved Claude transport, `map` resolves ownership, `status` checks state, `goal` dispatches a file, `send` follows up and `read` observes. Never infer those verbs are Codex equivalents or inline long shell-expanded briefs. Read typed/refused/ordinary-message outcomes before retrying; never double-drive a working session.
12. **Act by exact identity and preserve boundaries.** Resolve panes, launch PID/start time, worktree, checkout and owner before use. Restart through supported session controls while preserving flags; never copy credential files. A declined safety action is reported, never retried through another route. A new execution host needs approved scope, current installed instructions, runtime/policy/capacity checks and a bounded native acceptance/readback before real work.
